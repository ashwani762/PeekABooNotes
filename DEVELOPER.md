# PeekABoo Notes for developers

How to build it, how it's put together, and the details behind the features. For what it does, see the [README](README.md).

## Build and run

Needs Rust (edition 2024) and Windows 10 or 11.

```
cargo build --release
target\release\peekaboo-notes.exe
```

`cargo test` runs the unit tests: the note store, Markdown in and out of the editor (lists, emphasis, links, emoji, attachments), search, the zip writer, the MCP protocol, the shortcuts' keys, the Undo toast's stack, the string files and plural rules, and a check that `src/common` stays free of OS calls.

### Installers

- **Setup wizard (Inno Setup):** `powershell -ExecutionPolicy Bypass -File packaging\inno\build-setup.ps1` builds `target\setup\PeekABooNotes-Setup-<version>.exe` (add `-NoBuild` to reuse `target\release`). It installs per user without admin, offers a desktop shortcut and starting with Windows, and its uninstaller asks whether to delete the notes too. Needs Inno Setup 6 (`winget install JRSoftware.InnoSetup`). Install silently with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART`.
- **MSIX:** `powershell -ExecutionPolicy Bypass -File packaging\build-msix.ps1` builds a package in `target\msix\` (pass `-CertPath`/`-Password` or `-Thumbprint` to sign it). An installed copy starts with Windows through the package's startup task, and uninstalling it from Settings > Apps leaves the notes in Documents.

Both take the version from `Cargo.toml`.

### Developer switches

- `PEEKABOO_THEME=light|dark` forces an appearance.
- `PEEKABOO_PERF=1` logs frame times, and which parts asked for the frames, to `%TEMP%\peekaboo-perf.txt`.
- `PEEKABOO_TRACE=1` adds DEBUG lines (menu events and the like) to `logs\peekaboo.log`. Panic reports have raw `module+offset` stacks either way (see below).
- `PEEKABOO_CRASH=panic|fault|overflow` crashes on purpose right after startup, to test crash reporting.

A crash writes a minidump to `logs\crash-YYYYMMDD-HHMMSS.dmp` (the newest three are kept), and its report, with raw `module+offset` stack addresses, to the log and to `crash.log` in the notes folder. Open the dump in Visual Studio or WinDbg next to the matching build's `.pdb`. A minidump holds the threads' stacks, which can hold pieces of note text (what was being typed, saved or drawn), so treat one as private as the notes, and remember it sits in the notes folder, which may be synced; the log never has note text, and names the data folder with the user's own folder as `%USERPROFILE%` (`log::redacted`).

## Code map

The app is split so other platforms can be added beside Windows: `src/common/` is portable and never calls an operating system directly (a test enforces it), and each platform module (today `src/win/`) supplies the windows, text, editor and system services, plus the handful of functions in `crate::os` that `common` relies on (local time, the Documents folder, preferred languages, locale date formats, a system description).

| Path | Contents |
|---|---|
| `src/main.rs` | Entry point: picks the platform module |
| `src/common/` | The portable app: the note store (`store.rs`), interface strings (`i18n/`), search (`search.rs`), attachments (`attach.rs`), emoji (`emoji.rs`), the MCP protocol and tools (`mcp.rs`), the zip writer (`zip.rs`), the shortcuts' keys (`hotkey.rs`), what the Undo toast can take back (`undo.rs`), design tokens (`theme.rs`), springs (`anim.rs`), the log (`log.rs`) and small helpers (`util.rs`) |
| `src/win/` | Windows: `os.rs` (what `common` asks of the OS), `app/` (message loop, note lifecycle, menus, import, export and share, autostart, the MCP pipe), `ui/` (deck, note windows, All Notes, Settings, menus, toasts, tooltips, flying cards), `editor/` (RichEdit, links, quotes, code blocks and tables, and the checklist, colour-emoji and header-fade overlays), `render/` (software canvas, DirectWrite, frame clock), `crash.rs`, `theme.rs`, `util.rs` |
| `src/bin/peekaboo-mcp.rs` | The MCP bridge: stdin/stdout to the app's pipe |

### The editor

Notes are Windows' RichEdit (Msftedit), with a few things layered on:

- **Lists and checklists** are paragraph formats; a checklist item starts with a ☐/☑ placeholder that the checklist overlay draws as a circle. An item's nesting level is its start indent (RTF has no level of its own for it): nine levels, 0 to 8 (`store::MAX_LIST_LEVEL`, as in Word), the first five steps 320 twips each and the three after them 160 (`rich::level_indent`, `level_at`), so the deepest item's text still has over 100 DIP of a new note; Markdown has two spaces a level, and deeper Markdown comes in at level 8. Notes saved before kept to levels 0 to 5, which are where they were. Previews step in the same way. A quote under a list item (`quote_level`) goes one level further, under an item of level 8 at most. A numbered list counts on past a quote or code block under one of its items, on screen as in its Markdown: RichEdit starts a count again after a block (a table row) at the item's own start, and goes on from an item only to the next of the same start, so the item after such a block, and those RichEdit counted on from it, are given the number it has when the block is made or stepped in under the item, or the item is typed after it (`rich::count_on`). Quotes in quotes are RichEdit's nested tables, which go 15 deep: `> ` sixteen times or more comes in 15 deep, its text all there.
- **Colour emoji** are drawn over RichEdit's monochrome glyphs by an overlay. So that each takes as much room as its picture, every emoji is set in Segoe UI Emoji (`rich::style_emoji`, as a note opens and after each burst of edits; a symbol under U+FFFF such as ❤ as a symbol font's, or RichEdit binds it to Segoe UI Symbol): left to RichEdit's own fallback, 🚀 🎉 ❤ came out narrower than their pictures, which overlapped, and an emoji typed a character at a time had its skin tone or each person of a family laid out as glyphs of their own, a gap after the picture. Emoji variation selectors (U+FE0F) are kept out of the control as hidden private-use stand-ins, because RichEdit stops drawing list bullets once one is in a document.
- **Links** are RichEdit's named links (a hidden `HYPERLINK "url"` field before the shown text). RichEdit's own address spotting is off, because it picks those links' colour itself (white on paper dimmed for dark mode); typed and pasted addresses become named links when a space, Tab or Enter ends them, or the note opens. In code an address stays code, and a table's cell and row marks end a word like a space, so a link never takes in the end of a quote or a cell.
- **Quotes, code blocks and tables** are RichEdit table rows (`rich/blocks.rs`), so RichEdit draws, edits and stores them: a quote is one cell with a bar down its left border, a code block one shaded cell in Cascadia Mono (Consolas without it), a table any number of cells in a light grid with a tinted first row. Which is which is the cell margin it was made with (`\trgaph` in the RTF); borders a block doesn't show are drawn in the colour around it, since RichEdit outlines borderless cells in grey. Colours follow the note and the theme, and cells are refitted to the note's width when it's resized. A quote's paragraphs keep their own kind (bullets, numbers, checklist items), and a quote right after a list item steps in under it (Tab, Shift+Tab; the row's left indent). `> ` or ```` ``` ```` and Enter typed on a list item puts a quote or a code block in the item's place, under the item above it (Markdown indents both two spaces a level, a code block's fences and lines alike). A code block's cell mark has code's look too, so a new block's empty line types in it from the first letter, and its lines are spaced alike as they're typed: the air above the first line is set on the last line's paragraph as well as cleared from the others, since a restyle's selection ending at an empty last line left that line out, and it kept the air Enter had copied from the line above (6 px lower than the rest) until it held text. A quote can also hold blocks of its own (`> > nested`, a fenced code block or a table in a quote): their rows are nested in its cell, as RichEdit nests tables, and fit that cell's width; `rich::rows` and `rich::cells` see through them, and `rich::block_at` gives the innermost block. Code blocks and tables in a quote only come from Markdown (import, assistants); a quote in a quote comes from Tab too, in a quote that isn't under a list item: the lines it's on go into a quote of their own in its cell (`rich::wrap` there nests it, 15 deep at most), and Shift+Tab takes that quote apart again (`rich::unwrap`), out into the quote around it. RichEdit keeps an empty paragraph between two blocks, and after a block at the end of a quote; Markdown export skips both. Import takes one blank line on either side of a block as Markdown's way to set it apart, so export writes one more next to an empty paragraph there: a note goes out and back with the empty lines it had. A code block's language (```` ```rust ````) is kept as hidden text at the very start of its cell (`rich::code_tag`; a link's hidden instruction there is not one): the RTF stores it, while RichEdit draws nothing, moves the caret past it, never types into it and leaves it out of a copy; Enter, Tab and Backspace step past it (`rich::past_tag`), taking the block apart drops it, and the light text leaves it out. An empty code block (in the editor, one empty line) goes out as its two fences alone, and comes in from those or from fences with one empty line between them, so it stays empty there and back. Several-step changes (a new block, a checkbox) go through `rich::still`, which holds the view still and lets one Ctrl+Z take the whole change back; restyling blocks (colours, refitting to the width) is kept out of the undo history.
- **Undo** is the editor's own, 110 steps, for what was done since the note was opened. Restyling that follows from the text (the title's look, checklist boxes, hidden emoji marks, a theme) is kept out of it (`rich::unrecorded`, which nests inside `bulk`), so it never takes a Ctrl+Z of its own or empties the redo stack. A change made in several steps (a tick, a new block) goes back and comes again in one (`undo_group` / `redo_group`): `rich::still` collects its edits into one step of RichEdit's own (TOM's `BeginEditCollection`), however many lines it changes, so a checklist toggled over a hundred lines doesn't outrun the history (a picture's drag, which undoes and redoes RichEdit's steps itself, isn't collected). An assistant's change to an open note goes into the editor as an edit (`rich::replace_all_rtf`), so Ctrl+Z takes it back like one's own.
- **Previous versions** (`note/versions.rs`) reach past that: a note is kept as it was when it is first changed after being opened or after 10 minutes without a change (unless its last version is under 10 minutes old), and before an assistant changes it; saving as you type never keeps one. They're Markdown in `versions.json` beside the notes, at most 10 a note, 30 days and 5 MB in all, read and written only when one is taken, listed or dropped, so none of it stays in memory. It's written as `notes.json` is (a temp file, flushed, renamed), and when it's there but can't be read, no version is taken and nothing is written over it. An assistant can't wear the user's versions away: what an assistant wrote is marked so when it's kept (the note an assistant changed last, `assistant_made`), at most 5 of those stay a note and they're the first to go when there are too many, and a note's newest version of the user's own is never dropped for size. Ages follow the clock back at once but forward at most a day a prune, so a clock set years ahead for a moment can't age every version out; one taken "in the future" isn't aged. New notes take ids above every note `versions.json` still has versions for, so a note lost with an earlier notes file never lends its versions to a new one. The note's menu lists them in its Previous Versions submenu, which reads them only when it opens; putting one back keeps the current content as a version first, and in an open note is an edit Ctrl+Z takes back. A change that leaves the note reading as it did (a letter typed and taken back, an undo to where it was, a version put back that it already reads as) is no edit: no version is taken, and the note keeps its edited time and its place in the order (its RTF is still saved when only that differs, as for colours the theme gave a note made elsewhere). That holds when a pause saved the change in between, too: back to what it read when the stretch of work began, the note gets that edited time back, and the version its first save kept goes, being the note as it is. Its pictures and files (`attachments/photo.png` in the Markdown) are the note's attachments again when they're still in the folder (`note::own_attachments`). A note deleted for good takes its versions with it.
- **Alignment** (left, centre, right) is RichEdit's paragraph alignment; a picture is a paragraph of its own, so it aligns the same way. RichEdit insets the text on the left by its selection bar (`rich::SELECTION_BAR`, 225 HIMETRIC at the window's DPI) and nothing on the right, so a note window's right margin adds it: right-aligned text sits as far from the edge as left-aligned.
- **Bulk changes** (loading a note, applying a theme) freeze layout, drawing, notifications and undo until they're done, so a long note is laid out once instead of once per paragraph. Markdown out (`rich::to_markdown`, through `rich::reading`) runs frozen too, since it moves the selection through every paragraph and run, and puts the selection and the view back after: a 99,000-character note's text after a pause takes 9 to 14 ms rather than 51, its Markdown 32 to 38 ms rather than 250.
- **Pictures fit the note** (`rich/pictures.rs`): one wider than the text column (or its table cell) is narrowed to fit, keeping its shape, and grows back to its own size when the note is wider again. Its own size is the one it was made at (at most 240 DIP, from the PNG or JPEG header), or the one the user dragged its handles to. RichEdit keeps a picture's shown size only in its RTF, and nothing else about it (it writes its own scale, properties and crop), so fitting writes the picture through RTF again, as an edit outside the undo history and without change notifications, and remembers per editor what each picture it narrowed was narrowed from (by its attachment's link, and only while the picture is still at the size it was narrowed to); `get_rtf` puts those pictures back at their own size, so the note stores own sizes and fitting never marks it changed. What a fit found (each picture's place, own and shown size, indents) is kept per editor until anything in it changes (`pictures_changed`, from the note's `mark_dirty`), so a resize at the same width does nothing and a step of a drag writes again only the pictures whose size changes, without reading every picture first (`refit_picture_widths`; a hundred pictures: 0 ms and 33 ms, from 28 and 66). A press on a picture selects it or drags it out as a file, so RichEdit's sizing handles aren't offered today; should they be, a drag on them is an edit like typing: the note saves it after the pause, and one Ctrl+Z takes it back to the size before (RichEdit's own undo step for it when it makes one, else one made for it), while a fit on WM_SIZE never widens past it. Notes stored before this (`picture_sizes` in `notes.json`, `store::PICTURE_SIZES`) had pictures as last shown; at the first start, each narrower than its pixels make it gets its own size back, in the stored RTF, once.
- **Each editor's text object model** (`ITextDocument2`) is fetched once and kept (`rich::doc`, dropped in the editor's WM_NCDESTROY), and link colouring after typing moves one range from link to link: a note with hundreds of links costs a fraction of a millisecond per pause.
- The overlays look only at the text on screen, so they cost the same in a long note as in a short one, and read only that text (`rich::screen_text`, through the text object model: EM_GETTEXTRANGE leaves a table's row marks out), once for both after a message that drew; in one long paragraph, no more than 512 characters either side of what shows (a 100,000-character single line: 0.03 ms a key rather than 1.6 to 2.6). A key-down or key-up that changed neither the text's length, the selection nor the scroll position drew nothing (a caret moved by an arrow is Windows' own), so the overlays go on once a keystroke, not three times. The checklist circles are drawn on one canvas taken from the window and copied back in one go, so the screen never shows rows with only some of their circles. Colour emoji are too, each kept as the picture DirectWrite drew for it on a clear canvas (`emoji::SPRITES`, a few KB each, let go with the fonts at a trim): a colour glyph costs over half a millisecond to draw, and every read of the window waits on the screen, so a screenful of emoji went from 380 ms a paint to 17. A scrolled note fades into the paper at the top while there is text above, and at the bottom while there is text below (`editor/fade.rs`). A band is faded only right after RichEdit has drawn it fresh, and on a scroll only the rows the faded band was moved onto are redrawn, never the whole note.
- **The pointer** over a note (the checkbox under it for the hover ring and the hand cursor, the link under it for its tip) is worked out from the paragraphs around the character it's on (`rich::paras_around`), and kept while it stays on that character (`note/input.rs`, `Hover`): a move within one tests the point against what was found, and any message to the editor other than the pointer's lets it go. The cursor (WM_SETCURSOR, once a move) and a press work it out afresh at their own point (`checkbox_now`), so what they act on is never left from an earlier move, and a point left of a line that RichEdit gives as the mark ending the line above still finds that line's circle. A click, a typed space (`link_word_before`, `try_auto_list`), Backspace and Delete read just the paragraph or characters they need too. `pointer_finds_what_the_whole_text_did` checks it against reading the whole text at every point; `probe_pointer_moves` times it (80,000 characters: 22 µs a move within a character, 114 µs onto another, from 200 to 320).

### The deck's display

Settings › Deck › Show the deck on (shown only with more than one display, or while the chosen one is missing) keeps the monitor's device path from the display configuration (`QueryDisplayConfig`, then `DisplayConfigGetDeviceInfo` for each path's target name, `\\?\DISPLAY#DEL40F4#...`, and source name, the GDI `\\.\DISPLAYn` that ties it to an `HMONITOR`) in `deck_display`, and its name at the time in `deck_display_name`; empty is the main display, the default. GDI names aren't kept, since Windows renumbers them. `ui/displays.rs` lists the displays (main first, then left to right; the pop-up names the main one once, "Main display (DELL U2720Q)"; the monitor's own name, "Built-in display" for a laptop panel, else "Display n", with " 2", " 3" for alike ones) and works out the deck's (`deck::monitor_geo`). Both are kept until WM_DISPLAYCHANGE, WM_SETTINGCHANGE or WM_DPICHANGED (`displays::forget`) or the choice changes, and the list is read again when the pop-up opens, so nothing is enumerated per frame or per Settings rebuild. A chosen display that isn't connected leaves the deck on the main display without changing the setting, so it goes back by itself when that display returns; Settings shows it greyed as "(not connected)". The deck's scale, full-screen detection, card menus and tooltips, and where a note opened from the deck first appears all follow its display; a flying card is drawn at the scale of the note's own display. The shell's `ABN_FULLSCREENAPP` only says that a window somewhere went full screen or stopped, so at each one, when the displays change and when the deck moves, `deck/fullscreen.rs` looks down the other apps' windows in z-order for the first one on the deck's display (passing over small always-on-top ones) and steps aside only while that one covers the whole display and isn't a maximized window with a title bar.

### Limits

A note holds up to 100,000 characters (`MAX_NOTE_CHARS` in `store.rs`): typing and pasting stop there and the footer says the note is full; import skips longer files and assistants are told the text is too long. All of them count as RichEdit does, in UTF-16 units (most emoji are two). A note saved longer (from an older version) opens whole and just can't grow. In the editor the count is of what the note shows: RichEdit's own limit (`rich::limit_length`) lets through on top what it holds out of sight (named links' `HYPERLINK "url"` instructions, table row marks), and is set again after each burst of edits as links and tables come and go.

Caches are kept small and let go: DirectWrite keeps the 192 text layouts last drawn (up to 384 while a frame draws more), and with no note, All Notes or Settings open and the deck folded the app trims the layouts, emoji fonts and pictures, previews' decoded pictures and fonts, the deck's fonts and labels, the overlays' canvases and the last undo group (`app::trim_memory`), three seconds after a window closes or the deck folds; a closed editor's undo group, checklist colours and fitted pictures go with it.

Direct2D keeps what it made of a colour glyph (an emoji) for every opacity and every angle it was drawn at, for as long as its render target lives: text fading in and out over an animation grew the process by about 10 KB a frame, without end (64 peeks at a deck with emoji in its titles: 79 MB and climbing). So `dw::render` draws text opaque and fades the pixels it drew as it puts them down (the same picture), one Direct2D pass per opacity in a batch, and text turns in quarter degrees. The deck's spine labels are drawn once each, upright, and put down as pictures turned with their card (`Canvas::over_turned`, bilinear when turned, on whole pixels when not), so a frame of the fanned-out deck is 1.4 ms rather than 4.9 (a Direct2D pass per card); a label scrolling along a pointed-at spine draws a frame only when it has moved a whole pixel. `probe_peeks`, `probe_hover_memory`, `probe_frame_costs` and `probe_emoji_memory` in `deck/probe.rs`, and `probe_flights` in `ghost.rs`, measure it all off screen (`--ignored --nocapture`, in release).

Measured on the release build with 2,003 notes in a 2.4 MB `notes.json`: start to the deck in 0.16 s, a working set of about 5 MB at rest (once the app has trimmed it, with no note, All Notes or Settings open; the memory it has committed is more), All Notes open in under a second, a 3.6 MB save in 6 ms.

**A pause in typing** (250 ms; longer in a long note, up to 1.5 s at 100,000 characters, where a save costs a tenth of a second: RichEdit reading back a long paragraph full of links is most of it) saves the note: its RTF is made text in the hidden worker editor, `notes.json` is written, and the deck and All Notes update only that note's card and row (`app::note_edited`), drawing again only when they read differently. All Notes does nothing while it's closed, and makes all its rows again only while a search or a newest-first order depends on the note's text. With 500 notes (`probe_typing_pause` in `allnotes`, run with `--ignored --nocapture`) a pause costs about 0.4 ms for the text and 3 ms for the save; making every row and card again, as it once did, added 2.3 ms for All Notes, 1.6 ms for the deck and a full repaint.

Arrowing through the list, as typing a search, shows each note's quick preview; its editor is made once the keys rest (250 ms), not at every press. **Searching** in All Notes scores every note at each keystroke (`common/search.rs`). A `Query` keeps its buffers from note to note (the folded title and body, an in-order match's letters, the three rows of the edit distance, which one table per word serves for all three lengths it's compared at), folds the body only when a term needs it (a title match no body match could beat settles that term), and a snippet takes apart only its own line. The buffers go with the query, so nothing is kept between searches; folded copies of every note were left out, as they would hold four bytes a character for as long as All Notes is open. With 500 notes of about a kilobyte (`probe_search_keystrokes`, `--ignored --nocapture`) a keystroke costs 5.4 ms for all the rows, of which 2.9 ms is scoring, from 12 ms and 6.1 ms (8 ms when every row's title and preview were made again: a row now takes them from the list before it while the note's text is as it was, `row_again`); `same_results_as_before` checks that it finds, ranks and marks exactly as the earlier search did.

## Your data

Notes live in one readable file, `Documents\PeekABoo Notes\notes.json`:

- each note keeps its RTF and a plain-text Markdown copy (for search, previews and assistants);
- the file says which form it's in (`version`, `store::FORMAT`). Fields this version doesn't know, from a newer one, are kept as they are through a save (`extra` in `Note`, `Settings` and `Data`), and a file of a newer form is read but not written that session;
- writes are atomic: the JSON is streamed through a 64 KB buffer into a temp file, which is flushed to the disk (`sync_all`) before it's renamed over `notes.json`, so a save never holds a second copy of the notes in memory and a power cut can't leave an empty file. The layout stays pretty-printed: making the JSON takes 0.5 to 0.7 ms of a 3 ms save (500 notes, 1.5 MB) laid out or in one line alike, and most of the rest is the flush;
- `notes.backup.json` holds a copy of the last good file: written at start from what was read, then every 50 saves or hour, as atomically as `notes.json` (a temp file, flushed, renamed). At the day's first start the one there is kept first as `notes.backup-YYYY-MM-DD.json`; the three newest days stay. A backup is never replaced by a file of far fewer notes (under half, of four or more, as when a sync client brings back an old file): it's kept as `notes.backup-kept-<time>.json`, which the app never removes, and the new one goes in its place;
- if `notes.json` can't be understood (damaged), it's set aside as `notes.unreadable-<time>.json`, the newest backup that can be read opens instead, and a toast names the file; if it can't be read at all (locked), the backup opens and nothing is written this session. Missing with a backup beside it, the backup opens (a toast says so) and is saved as `notes.json`. Missing from a folder that held notes (a backup, attachments or `versions.json` are there), or from one that can't be reached (a USB stick, second drive, network share or synced folder not there yet), the session starts empty and writes nothing, so the real notes are untouched when the folder is back. Only a new folder starts fresh, and even then a `notes.json` that turns up later (a sync client bringing the notes down) is never written over: that session stops saving;
- before each save the app checks that `notes.json` is the one it last read or wrote (size and time, then its bytes). If another program or computer changed it (OneDrive on two PCs, a shared portable folder), that copy is moved aside as `notes.conflict-<time>.json`, never deleted, a toast says so (once a session), and then the notes are saved. Nothing is merged: the conflict copy is there to look through by hand. A temp file a failed save leaves is removed;
- attachments are copied into `attachments\` beside it and linked by name, each file once per drop, import or assistant's note however often it's linked (an import links a file the folder has already, by name and bytes, rather than copying it again as "photo (2).jpg"), and none over 100 MB (`attach::MAX_FILE_BYTES`; a bigger one is refused and logged). Dragged out of a note, an attachment is offered as a copy, never a shortcut into the folder. A note deleted for good (once its own Undo has passed, or at quit) takes its files with it, except those another note or a saved version still links, and only when the notes in use are all there are (notes.json read whole and written this session, no `notes.unreadable-*.json` or `notes.conflict-*.json` beside it). At start, a one-off thread sweeps out files nothing links any more (a picture taken out of a note, say: `sweep_attachments` in `app/notes.rs`) into `attachments\.trash\<day>\`, where they stay 30 days before the sweep empties that day. It keeps whatever any note (archived ones and those awaiting Undo too), saved version or the clipboard links (files copied in Explorer too), in any case, and any file younger than a day or than notes.json's last save (it may belong to notes synced from elsewhere and not seen yet). It does nothing under the same conditions as deleting does, nor unless versions.json can be read, and it never takes every file in the folder at once.

There is no network access and no telemetry.

`logs\peekaboo.log` in the same folder records what happened (start and exit, load and save errors, import and export counts), never what the notes say. It rotates at 512 KB, keeping one older file (`peekaboo.1.log`).

**Portable mode:** an empty file named `portable` next to `peekaboo-notes.exe` keeps the notes in `PeekABooData\` beside the exe instead.

## Undo

Archiving, deleting, restoring from the Archive and importing each go on a stack (`common/undo.rs`, `app::Undo`) with ten seconds of their own; the toast shows the newest, one of a kind in a row joined ("2 notes deleted"), and its clock waits while the pointer is on it. Undo takes back the newest, and the toast then shows the one before it with the time it has left, so a newer action never makes an older delete final early: each is made final when its own time runs out (a deleted note's versions and files go then, and a file a note still waiting in the stack links stays). Deleted notes go back where they were, last taken first (`Store::put_back`). A note keeps its place in the deck while it's archived (`Store::reorder` numbers archived notes' places along with the rest), so a restored one comes back between the notes it was among. While only the clock runs, the toast is drawn on a 100 ms timer, and again only when the ring has moved a pixel or the seconds change; its window is named after what it says.

## Import, export and share

- **Export** writes one Markdown file per note into a folder you pick (the picker remembers it). It never overwrites a file; a name already in the folder gets "(2)", and a title Windows keeps for a device (`CON`, `NUL`, `COM1` and the like) gets a leading `_`.
- **Front matter** (`common/frontmatter.rs`) at the top of each file keeps what Markdown can't: the colour by name, and, only when they differ from a new note's, `pinned: true`, `archived: true` and `in_deck: false`, then `created` and `updated` in UTC (`2026-10-25T14:03:07Z`). Import puts them back and leaves the block out of the note (and one blank line after it, a hand-written file's gap: a note that starts with an empty line goes out with one more there), so Export All and then Import brings every note back as it was. Only a block of exactly these keys counts: another program's front matter, or a note that just starts with a `---` line, comes in as text, as a file without front matter always has.
- **Import** reads `.md` and `.txt` files (UTF-8, or UTF-16 with its byte order mark, as Notepad's "Unicode" saves) and turns their Markdown into real formatting: `**bold**`, `_italic_`, `~~strike~~`, `<u>underline</u>`, bullets, numbers, `[ ]` / `[x]` checklists, nested lists, `[links](https://...)`, `> ` quotes (with lists inside, `> - item`, quotes and code blocks inside, `> > nested`, and under list items, `  > text` or `- > text`), fenced code blocks with their language (a fence longer than any inside it is written when the code holds one), pipe tables (`:---:` and `---:` align a column) and `<p align="center">` / `"right"` lines; a list item's alignment goes inside its marker (`- <p align="center">item</p>`), and a centred or right-aligned title is written `<h1 align="center">Title</h1>`. Headings below the title come in as plain text. Plain text that only looks like a marker is written escaped (`\- not a list`, `  \- indented`, `\>>> print`, `\-` alone, `\\- a backslash`, a first row `\| a |` over a `| --- |` line) and comes back as text, while an empty item (`- `, `2. `) comes back as one, as is a list item's text that would read as a quote or a checkbox (`- \> text`, `- \[ ] text`), and typed text that would read as a mark, a tag or a link, where it would (`\_\_init\_\_`, `\~\~`, `\<u>`, `\[a](url)`; not `snake_case` or `2 ** 3`), also after a backslash that's text (`C:\\_temp`). Table cells hold plain lines, so list markers in a cell are its text. A file whose note would say exactly what one here says (title and text, `Store::says`) is left out, and the button and the toast say so ("3 imported, 2 already here"; "1 note imported, 2 already here"; with nothing new, "2 notes already here"), as they say how many files couldn't be read, too long for a note or not to be read at all (", 1 couldn't be read"; with nothing else, "2 files couldn't be read", which the button shows as a failure); the Undo toast takes the notes an import added out again. The file picker starts in the folder the last import came from (`import_dir` in `notes.json`).
- **Attachments** go along: export copies them into an `attachments` folder beside the Markdown and links them relatively (`![photo.jpg](attachments/photo.jpg)`), reusing a file already there only when its bytes are the same (another file of that name gets a free one); import copies linked local files back in. Import skips a file larger than a note could be (`MAX_IMPORT_BYTES`) without reading it, and Share streams each file into the zip rather than reading it whole.
- **Readable anywhere:** plain UTF-8; lines end in Markdown's line break (two spaces) so viewers keep them apart as the note has them, and text right after a list has the blank line Markdown needs there, which import takes out again (an empty line the note had there goes out with one more, as next to a block); an address that links to itself is written as just the address.
- **Share** writes the same files for the selected notes into one zip (stored, not compressed) under `%TEMP%\PeekABoo Share` and hands it to the Windows share sheet; without one, Explorer shows the zip.

A round trip keeps nesting, emphasis, links, attachments, ticked items, colours, pins, the archive, the deck and dates intact.

## AI assistants (MCP)

Off until **Settings > Data > Allow assistants (MCP)**. **Connect** writes the bridge into the chosen app's own MCP settings (keeping a `.bak` of the file beside it), and the app has to be restarted. Where the app isn't installed (its settings folder is missing), or takes the setup in a form of its own, the snippet goes on the clipboard instead:

| App | Where it goes |
|---|---|
| ChatGPT (desktop app) | Copied: add an MCP server of type STDIO, with the command |
| Claude Desktop | `%APPDATA%\Claude\claude_desktop_config.json` (`mcpServers`) |
| Claude Code | Runs `claude mcp add -s user peekaboo-notes -- ...`; copied if `claude` isn't on PATH |
| Gemini CLI | `~/.gemini/settings.json` (`mcpServers`) |
| Codex | `~/.codex/config.toml` (the `[mcp_servers.peekaboo-notes]` table) |
| Cursor, Windsurf, LM Studio | `~/.cursor/mcp.json`, `~/.codeium/windsurf/mcp_config.json`, `~/.lmstudio/mcp.json` (`mcpServers`) |
| VS Code (Copilot) | `%APPDATA%\Code\User\mcp.json` (`servers`) |

Any other app that runs local MCP servers works the same way: its command is `peekaboo-mcp.exe` from the app's folder (from the MSIX, just `peekaboo-mcp.exe`). ChatGPT on the web only reaches servers on the internet, so it can't use this one.

The tools: `list_notes` (lists, or searches forgivingly), `read_note` (Markdown, colour, dates, attachments), `create_note`, `update_note`, `append_to_note` (keeps the note's formatting), and `set_note_state` (archive or restore, pin, colour, deck). There is no delete, and `update_note` refuses an empty (or blank) replacement, which would amount to one; a version of the note is kept before every change. Local files linked in an assistant's Markdown (`![chart](C:/path/chart.png)`) are copied in as attachments when they're in the user's Pictures, Documents, Downloads, Desktop, Videos or Music, or the temp folder, and never from the notes' own folder (`note::assistant_folders`), though a link to a file already in its attachments (as `read_note` writes them, `attachments/photo.png`) is that attachment again, not a copy; an imported Markdown file brings in only files from its own folder. Links elsewhere stay links, so neither can copy in an arbitrary file.

How it works: the assistant starts `peekaboo-mcp.exe`, which carries its JSON-RPC messages over the named pipe `\\.\pipe\PeekABooNotes.mcp.<user's SID>` to the running app (starting it if needed). The app answers on its UI thread, so open notes, the deck and All Notes update as the assistant writes. The pipe only takes connections from this computer and this user, and only while the switch is on. Another user on the computer can't get in between (`win/pipe.rs`, which the bridge takes in by path): the name is the user's SID rather than their user name, the app makes the pipe's first instance only if nobody holds the name already (`FILE_FLAG_FIRST_PIPE_INSTANCE`) and with an owner-only DACL (no pipe at all without one), and the bridge talks only to a server whose process runs as its own user (`GetNamedPipeServerProcessId`), connecting at the identification level so the server can't act as it.

## Shortcuts

**Anywhere** (if another app already uses one, PeekABoo Notes goes without it; Settings › Shortcuts shows it as off and the log says so)

| Keys | Action |
|---|---|
| Ctrl+Alt+N | New note |
| Ctrl+Alt+A | All Notes |
| Ctrl+Alt+L | Show the Archive |
| Ctrl+Alt+O | Reopen last note |
| Ctrl+Alt+H | Show or hide the deck |
| Ctrl+Alt+E | Move the deck to the other edge |
| Ctrl+Alt+K | Give the deck the keys (again, or Esc, to give them back) |

These are the defaults. Settings › Shortcuts gives any of them other keys: a click on its keycaps (or Enter or Space on the focused row) has the row wait for keys, with "Press keys" where the keycaps were and the modifiers held so far ahead of it. The next key that isn't a modifier, with the modifiers held, is taken if it's two of Ctrl, Alt, Shift and Win and a letter, a digit or F1 to F12 (`common/hotkey.rs`, `Combo::from_press`); otherwise the row says why and keeps waiting. Esc, a click anywhere else or the window losing the keys cancels; Backspace or Delete turns the shortcut off. Keys another shortcut has ("Already used for “New note”"), keys that type a character on one of the user's layouts (the AltGr test below, with Shift when it's held) and keys `RegisterHotKey` refuses ("Taken by another app", tried under an id of its own) are refused and the old keys kept; the reason shows in the row for four seconds, as how to cancel does while it waits: beside the keys (on two lines when it's too long for one), or in the row's subtitle when it has one (why it's off), so a row never changes height. While a row waits, every shortcut is unregistered (`pause_hotkeys`), so the keys pressed reach Settings, ours too, and they're registered again with the keys they have now when it stops (`resume_hotkeys`); the key-ups after it are kept from the window menu. Reset to Defaults, at the end of the group, brings back Ctrl+Alt and the letters. The keys are kept in `notes.json` as `settings.hotkeys`, each changed shortcut's name and its keys as text (`{"new_note": "Win+Shift+N", "reopen": ""}`, "" for one turned off); a shortcut with its default keys isn't written, so the field is left out until one changes, and a name or keys this version can't read stay as they are. The tray menu, the deck's tooltips, Settings and All Notes' empty list (which leaves the shortcut out while New Note's is off) show the keys in use (`hotkey_text`).

Ctrl+Alt is also AltGr, and on many keyboards AltGr and a letter types a character (€ with E on German, French and Spanish keyboards; ą, ę, ł, ń, ó on Polish ones). A hotkey would swallow it in every app, so `app/hotkeys.rs` asks each of the user's keyboard layouts (`GetKeyboardLayoutList`, then `ToUnicodeEx` with Ctrl and Alt down) whether Ctrl+Alt and the letter types something, and leaves out every shortcut that does. The layouts are looked at again on `WM_INPUTLANGCHANGE` and `WM_SETTINGCHANGE`, and when a hotkey arrives from a window whose layout wasn't known yet; that press then does nothing if the new layout types a character with it. Menus and tooltips leave out a shortcut that's off. A shortcut steps aside only for a character people write every day: any symbol (such as €), and letters on a layout for another language than English; an English layout's extra accented letters (English (India) types ā ē ō ṇ ḥ with AltGr) don't take a shortcut away. Stepping aside for other languages' keyboards is a beta: only English layouts have been tried on a real machine, and Settings says "beta" on such a shortcut.

**In a note**

| Keys | Action |
|---|---|
| Ctrl+N | New note |
| Esc / Ctrl+W | Close |
| Ctrl+B / I / U | Bold / italic / underline |
| Ctrl+Shift+X | Strikethrough |
| Ctrl+Shift+8 / 7 | Bulleted / numbered list |
| Ctrl+Shift+L | Checklist |
| Ctrl+Enter | Tick or untick the checklist item |
| Tab / Shift+Tab | Indent / outdent a list item (Backspace at a nested item's start outdents it too; at the top level it takes the bullet off); in a table, next / previous cell (Tab in the last cell adds a row); in a code block, indent / outdent the line; on other lines Shift+Tab takes a tab off the line's start, and never types one |
| Enter in a code block | A new line with the same indent; an empty line stays, and a second empty line at the block's end leaves it (both go) |
| Ctrl+L / E / R | Align left / centre / right |
| Ctrl+' | Quote |
| Ctrl+Shift+M | Code block |
| Ctrl+Shift+T | Table |
| Ctrl+K | Link the selected text, or change the link at the caret |
| Ctrl+. | Next colour |
| Ctrl+Shift+P | Keep on top |
| Ctrl+Shift+A | Archive |
| Ctrl+Shift+Del | Delete (with Undo) |
| Ctrl+[ / Ctrl+] | Previous / next note |

**In All Notes:** Ctrl+F goes to the search box, its text selected, from anywhere in the window, the note being edited too; Ctrl+Shift+A archives or restores and Ctrl+Shift+Del deletes the selected notes (plain Del too, when the list has the keys); while the Undo toast shows, Ctrl+Z (outside the note being edited) takes back the newest archive, delete, restore or import, and the next press the one before it, as does the tray menu's Undo; Ctrl+Tab leaves the note being edited. Tab and Shift+Tab move through All Notes and Settings with a focus ring; Space or Enter presses, the arrow keys move along segments and swatches. In menus, the arrow keys reach every row, colour and format button; Right or Enter opens a submenu (a row with a chevron, such as Previous Versions) and Left or Esc goes back out of it. A typed letter goes to the next row starting with it, from the one the focus is on (case and accents aside, in any script), as it goes to the next card in the deck (`focus::by_letter`). Paste is always plain text, so notes keep a consistent look.

**In the deck** (once Ctrl+Alt+K has given it the keys): Up and Down move a focus ring along the cards and on to the "+N" tile and the plus button, stopping at the ends; Home and End go to the ends, Tab and Shift+Tab come round; a letter jumps to the next card whose title starts with it. Enter or Space opens what the ring is on, Shift+F10 or the Menu key opens its menu (beside the card, and the keys come back to the deck when it closes), and Esc or Ctrl+Alt+K again hands the keys back to the window that had them (the desktop, if it has gone). The deck never activates on a click (`WS_EX_NOACTIVATE`): only the hotkey brings it to the foreground, and it lets the keys go the moment they go elsewhere (a click in another app, a note opening), folding as it does when the pointer leaves. While it has them it stays open, with no timer running (a deck hidden by the user or for a full-screen window comes out for as long as it has them); the ring lights its card as the pointer would and pulls it out after the same rest, and the pointer moving onto a card (or the "+N" tile, or the plus button) takes the ring there, so Enter opens what's lit. Where focus goes (`deck/keys.rs`) is pure logic with its own tests. Ctrl+Alt+D would have been the obvious key, but it is Magnifier's docked view. With Reduce Motion (or Windows' animation effects off) the deck fans out and folds in one step, with no cascade.

## Languages

English, German, Spanish, French, Hindi and Japanese are built in. The interface is in English unless **Developer mode** is on (Settings › Data › Developer, `developer` in `notes.json`, `Settings::ui_language`): only then does the Language row show there, and the language it picks (kept in `language` while developer mode is off) apply. It picks a built-in language or **Same as Windows** (Windows' preferred display languages: the exact tag, then the base language, then English). Dates and times are formatted by Windows for the chosen locale.

Interface text lives in Android-style resource files, one per language: `src/common/i18n/strings/strings.<tag>.xml`.

```xml
<resources>
    <string name="menu_new_note">New Note</string>
    <string name="window_all_notes">All Notes — %1$s</string>
    <plurals name="notes_count">
        <item quantity="one">%d note</item>
        <item quantity="other">%d notes</item>
    </plurals>
</resources>
```

- **Placeholders:** `%s` and `%d` in order, or `%1$s` and `%2$d` by position.
- **Plurals:** the CLDR categories (zero, one, two, few, many, other).
- **Fallback:** English is the reference; any key a translation lacks falls back to it.
- **Beta:** only English has been read through by people who speak it, so the other languages are behind developer mode, and its language picker marks them "(beta)".
- Buttons and menu items never end in "…".

**Adding a language**
1. Copy `strings.en.xml` to `strings.<tag>.xml` (for example `strings.it.xml` or `strings.pt-BR.xml`) and translate the text.
2. Either add the file to `BUILTIN` in `src/common/i18n/mod.rs`, or drop it into a `lang` folder next to `peekaboo-notes.exe` (or in the notes folder).

Files in `lang` are read at startup and override the built-in strings, so a translation can be tried without rebuilding. Every build copies the built-in files to `target\<profile>\lang\`. `cargo test` checks that every built-in language has exactly the keys and placeholders of English.
